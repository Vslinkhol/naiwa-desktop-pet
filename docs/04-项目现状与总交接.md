**连带处理**（不改就是新引入的毛病）：

- 合成笑声原本只有 1.4~2.0 秒，动画变 15.4 秒会有 **13 秒静音尬笑** → `core/audio.js` 改成**从素材清单读时长**并按「笑一阵、喘一口」分段合成。
- 工作模式「勾选待办笑一下」复用同一个 `laugh`，会变成笑 15 秒、且期间 `isReacting()` 为真**点不开面板** → 新增 `laugh_short` 槽位（同一批 PNG 的 27~53 帧，1.8 秒，不额外占体积）。

### 2.2 第五次会话改了什么（用户提的两条）

| # | 用户原话 | 根因 / 做法 |
| --- | --- | --- |
| 1 | 拖动奶蛙时不要变成小螃蟹图案，保持静态图不变 | `assets/manifest.js` 里 `drag` 是 `kind:'none'`（没有真实拖拽素材）→ 表现层退回**内置占位卡通蛙**，而 CSS 又给它写了「手脚乱晃」，看起来就是一只小螃蟹。做法：`renderer/app.js` 加 `DRAG_ANIM = false`，拖拽全程不动画面，反馈只靠光标形状 |
| 2 | 右键单击弹出操作窗（含退出按钮），切模式改成右键双击 | 新增 `#pet-menu`（DOM 在 `index.html`、样式在 `core/style.css`、逻辑在 `app.js` 的「右键操作窗」一节）；新增 `window.naiwa.quit()` → `main.js` 的 `app:quit`（**和托盘那一项走同一条路**：`app.isQuitting = true` + `app.quit()`，否则关窗口不等于退出） |

**操作窗的三个设计点**（都不是随手写的）：

- **位置固定在奶蛙正上方居中**，不贴光标：奶蛙就待在窗口最底部，贴光标会盖住它自己的头，还容易被窗口下边缘切掉。夹在窗口内是硬要求（窗口只有 460×640）。
- **不做「延迟 400ms 等第二击」**：那会让每次右键菜单都慢半拍。改成先立刻弹出，若 400ms 内又来一次右键，就收起菜单并切模式（菜单闪一下，正好当双击的反馈）。**双击分支必须把 `lastContextAt` 清零**，否则下一次右键会被当成第三次连击、切模式乱套。
- **参与点击穿透判定**：`isInteractiveAt()` 认 `#pet-menu`，光标移开 / Esc / 点任一项 / 切模式 / 光标离开窗口都会收起（`mousemove` 与主进程光标推送两条路都接，幂等）。

**连带处理**：

- 两套冒烟测试里**所有「右键切模式」的用例都失效了**（它们发的是单次右键，现在只会弹菜单）：`__smoke.js` 的 `contextMenuAt` 和 `__smoke.work.js` 的 `RIGHT_CLICK` 都改成**双击**（两击间隔 120ms），另加 `contextMenuOnceAt` / `RIGHT_CLICK_ONCE` 给菜单用例。
- 新增验收项：`S17`（右键单击弹操作窗）、`S18`（拖拽保持静态图）、`W28`（工作模式里「打开面板」项可见且点了真能开）、以及探针里的**像素级拖拽比对**和**退出按钮真的结束进程**。

**原生笑声这一条有个容易漏的细节**：`core/audio.js` 对**短提示音**会做 ±6% 的音高随机
（避免每次一模一样）。套到 15 秒的整段录音上就变成明显变调、像快进。
所以加了 `play(name, opts)` 的 `opts.jitter`，两处大笑调用都传 `{ jitter: false }`；
**链路要打通三层**（`modes/relax.js` → `app.js` 的 `ctx.audio.play` → `core/audio.js`）——
`ctx.audio.play` 原来只转发 `name`，参数会在中间被吃掉。

**打包踩到的两个坑**（都在本机环境，写进 §3.4 / §3.5）：

- `%TEMP%` 不可写时，NSIS 的「提取卸载器」步骤会失败，报错却只说
  `process failed 2`；把 `TEMP`/`TMP` 指到可写目录就通了。
- electron-builder 每次都会重新下载 Electron（100 MB），网络一抖就 `Timeout awaiting 'request'`；
  配 `"electronDist": "node_modules/electron/dist"` 直接用本地已装好的那份，既快又稳。

**产品上顺带修的一处**（有实测证据）：单实例锁失败时，原来一律提示
「奶蛙已经在运行，或者上一次的进程卡住了」。但打包版在受限环境里实测到的是
`Lock file can not be created! Error code: 5`（**数据目录不可写**），
用户照着提示去任务管理器找残留进程永远找不到。
现在先探测数据目录可写性，两种情况给**不同的提示**和**不同的解决办法**。

**发布这件事在本机有几个前提**（都踩过，别再花时间）：

- **git 在 `D:\Develop kits\Git`**（不是标准路径，注册表里还指着已经不存在的 `D:\Git`）。
- **这台机器的 schannel 坏了**（`SEC_E_NO_CREDENTIALS`），curl / .NET / git 默认后端全都连不上 TLS；
  git 必须 `-c http.sslBackend=openssl`，**Node 反倒没事**（它就是 OpenSSL）。
- **直连 github.com:443 不通**，要走 Clash 的系统代理 `127.0.0.1:7890`；
  Node/npm 自己吃系统代理，**git 必须显式配 `http.proxy`**（已写进 `.git/config`，不会推到远端）。
- **git over HTTPS 用 PAT 只能走 Basic**（`x-access-token:<token>` 的 base64）。
  用 `AUTHORIZATION: bearer` 会得到 `remote: invalid credentials`，那个报错会把人引向「令牌错了」的歧路 ——
  实际令牌没问题，是认证方式不对（用 `GET /repos/...` 探一下就知道了）。
- 细粒度令牌的 `GET /repos/...` 返回的 `permissions.push` 是**用户本人**的权限，**不代表令牌的权限**；
  要验令牌得做一次真实写操作（建个临时 ref 再删掉）。另外 `Repository access` 选
  「Public repositories」= **只读**，权限框里选了什么都会被它压住 —— 这就是第一次 403 的原因。

## 3. ⚠️ 环境坑（最重要的一节）

**这三个坑的共同点是：没有任何报错，屏幕上什么都不发生。** 不知道的话能查几小时。

### 3.1 Electron 建不了 userData 目录 → 静默崩溃

- **现象**：`npm start` 之后**什么都没出现**，没有窗口、没有报错、进程直接退出。
- **根因**：Electron 进程创建 `%APPDATA%\naiwa-pet` 失败，报
  `EPERM: operation not permitted, mkdir '...'`；
  而 Chromium 拿不到 userData 会直接崩 —— **访问违例 0xC0000005，退出码 -1073741819**。
- **最诡异的地方**：**PowerShell / cmd.exe / 普通 Node 都能建这个目录，只有 Electron 不能**
  （DSH 在 Windows 上用受限令牌启动子进程）。所以「我手动建得出来啊」不能证明 Electron 建得出来。
- **已修**：`scripts/ensure-userdata.js` 在启动 Electron **之前**用普通 Node 把目录建好，
  `npm start` / `dev` / `start:force` 都已接上。目录已存在时是空操作。
- **诊断命令**（GUI 程序的标准输出接不住，必须重定向到文件）：

  ```powershell
  Start-Process '.\node_modules\electron\dist\electron.exe' `
    -ArgumentList '--no-sandbox','--enable-logging=stderr','.' `
    -RedirectStandardError err.txt -Wait
  Get-Content err.txt
  ```

### 3.2 残留的 Electron 进程杀不掉 → 占死单实例锁

- **现象**：和 3.1 一模一样 —— **什么都没出现**。
- **根因**：`main.js` 里 `if (!app.requestSingleInstanceLock()) app.quit();`
  锁被上一次的残留进程占住，于是静默退出。
- **要命的地方**：**那些残留进程连 `taskkill /F` 都杀不掉**，报「拒绝访问」，
  任务管理器也结束不了 —— 它们跑在受保护的安全上下文里（DSH 启动的进程都这样）。
- **解法**：
  - **重启系统**（最干净）
  - 或 `npm run start:force`（用 `NAIWA_ALLOW_MULTI=1` 跳过单实例检查）
- **已修**：锁被占时会**弹一个错误框**说明原因和三个解法。
  以前是完全静默 —— 桌宠是双击启动的，没有控制台可看，只打 stderr 等于没打。
- **第六次会话又改进了这个弹框**：锁失败有两种完全不同的原因，原来一律说「已经在运行」。
  实测抓到过另一种 —— 打包版在受限环境里报 `Lock file can not be created! Error code: 5`，
  也就是**数据目录不可写**，此时去任务管理器找残留进程永远找不到。
  现在先探测数据目录可写性，两种情况给不同的提示和解法。

### 3.3 `naiwa-pet/assets/**` 整个目录树对**沙箱子进程**拒写

- 第三次会话记的是「rename / unlink 报 `EPERM`，普通写入是允许的」。
  **第四次会话实测更严重：连新建文件和追加已存在的文件都被拒**
  （`Access to the path ... is denied`）。
- 逐目录量过边界，只有这一个目录特殊（实测同一次运行的对照）：

  | 路径 | 沙箱子进程写入 |
  | --- | --- |
  | `<工作区>\.tmp-w.txt` | ✅ |
  | `<工作区>\naiwa-pet\.tmp-w.txt` | ✅ |
  | `<工作区>\naiwa-pet\assets\.tmp-w.txt` | ❌ 拒绝 |
  | `<工作区>\naiwa-pet\assets\manifest.relax.js`（追加空串） | ❌ 拒绝 |
  | `<工作区>\.assetwork\.tmp-w.txt` | ✅ |
  | `<工作区>\.naiwa-probe-tmp\.tmp-w.txt` | ✅ |

  根因是权限继承链：工作区根给当前用户的那条完全控制项**不可继承**
  （ACE 上没有 OI/CI），所以 `assets` 只继承了沙箱专用 SID 的授权，
  而沙箱令牌是受限令牌、不认当前用户自己的 ACE。
  用 `diagnose-windows-sandbox-acl` 那个脚本给 `assets` 补了当前用户的完全控制项
  （已备份 + 可回滚，备份在 `<工作区>\acl-recovery\`），**但仍不够** ——
  受限令牌访问检查根本不看当前用户的 ACE，所以**沙箱内写入依然被拒**。
- **结论（对干活的影响）**：
  - 程序**只读**素材，`npm start` / `npm run check` / 冒烟测试全都不受影响。
  - **重新生成素材（`.assetwork/build.js`）必须在非沙箱环境里跑**，
    否则每一步 `writeFileSync` 都是 EPERM。第四次会话就是这么做的（一次性更宽权限）。
  - 因为不能删文件，`build.js` **不再做 `rmSync`**：帧名是固定编号、重跑原地覆盖；
    帧数变少时留下的旧帧只能人工清（脚本会扫一遍并报出来）。
  - 「先把素材移走再移回来」的测试思路**依然不成立**；
    「素材缺失」测试要用**复制整个项目到别处、在副本里破坏素材**
    （🅱 已把这个做法写进 [`03-工作模式交付.md`](03-工作模式交付.md) 第 5 节）。

### 3.4 其他环境事实

- **必须 `--no-sandbox`**（仅限开发期在工作区里跑）。不加的话 Electron 起不来（连 `--version` 都崩）。已写进 npm scripts。

  > ⚠️ **这条既不是 DSH 会话的限制，也不是「这台机器」的毛病，而是「应用所在目录」的毛病**
  > （第七次会话查清，推翻了前一版「是这台机器本身」的说法）。
  >
  > **实测**：`D:\dsh data\travel agent` 整棵树带
  > `Mandatory Label\Low Mandatory Level:(OI)(CI)(NW)`，里面的 exe 全部**继承 Low**（`(I)(NW)`）；
  > Chromium 130 的沙箱初始化在这种目录下会**主动急停**
  > （`IMMEDIATE_CRASH()`，字节 `CC 0F 0B` = `int3;ud2`，退出码 `-2147483645` / `0x80000003`，
  > **零输出、无弹框** —— 崩在日志初始化之前、JS 之前）。
  > 把**同一个官方 exe** 复制到任何普通目录，**不加 `--no-sandbox` 也能正常启动**。
  >
  > 第七次会话自测（两次独立复现）：
  >
  > | 位置 | `--version` | 直接启动（不带参数） |
  > | --- | --- | --- |
  > | `<工作区>\naiwa-pet\dist\win-unpacked\` | **`-2147483645`**，零输出 ✗ | 秒退 ✗ |
  > | `D:\Apps\naiwa-pet\`（普通目录） | `0` + `v33.4.11` ✓ | **4 个进程 + 窗口标题「奶蛙」** ✓（并写出 `naiwa-data.json`） |
  >
  > **快速判定**（两条任一命中即是这个坑）：
  > 1. `icacls "<应用目录>"` 里出现 `Mandatory Label\Low Mandatory Level`；
  > 2. `"Naiwa Desktop Pet.exe" --version` 的退出码是 `-2147483645`（正常应是 `0` 且打印 `v33.4.11`）。
  >
  > **解决办法**：把应用放到普通目录。**安装版装到 `%LOCALAPPDATA%\Programs\…` 天然没问题**；
  > 工作区里的开发版则必须带 `--no-sandbox`（npm scripts 里已经带了，见 §3.7）。
  >
  > **残余不确定性（措辞要留余地）**：「就是那条 Low 标签导致的」目前是**排除法**结论 ——
  > 它是同一 exe 在两种环境下唯一未被复制过的差异（ACL、路径长度、空格、盘符、深度、工作目录、
  > 签名、ASR、Exploit Protection、IFEO、AppLocker 都已排除）。要 100% 闭合需要管理员权限做对照实验：
  > 给一个普通目录单独贴上 Low 标签，看是否复现 `0x80000003`。**这个实验还没人做过。**
  >
  > **对打包产物的影响**：`启动奶蛙.cmd` 的兜底（先正常启动、2 秒内没起来再带 `--no-sandbox` 重试）
  > **仍然有效、应当保留**，但它**只在「应用目录被标成低完整性」这类环境下降级** ——
  > 普通用户从安装目录或普通文件夹启动根本不会触发，默认保持沙箱。**不要因为这条把 `--no-sandbox`
  > 写死进产品**（见 §3.7 的红线）。
- **屏幕是 2560×1600 物理 / 1707×1067 逻辑（150% DPI 缩放）**。
  写截图或自动化脚本时：`CopyFromScreen` 按**物理**像素、DPI 感知进程里的 `SetCursorPos` 按**逻辑**坐标。
  **搞混了会截到完全不相干的区域**（实测踩过：以为在截奶蛙，其实截的是聊天窗口）。
  正确做法是先 `SetProcessDPIAware()`，然后统一用物理坐标（逻辑 × 1.5）。
- **打包前要排除原始素材**：`assets/解压模式素材/` + `assets/工作模式素材/` 合计约 **7.8 MB**
  （占 `assets/` 的 86%），程序完全不读，但会被打进安装包。
  因为 3.3 那条，「移出去」做不到 —— 正确做法是在打包配置里排除（`electron-builder` 的 `files` 加 ignore）。
  **第六次会话已落地**：`package.json` 的 `build.files` 里写了两条 ignore，
  最终 `app.asar` 只有 **11.6 MB**（231 帧 + 音频 + 代码），原始素材 0 个条目。

### 3.5 打包（electron-builder）在本机踩到的两个坑

**① NSIS 的「提取卸载器」会失败，报错极含糊**

- **现象**：`⨯ dist\...-setup.exe process failed 2 / Exit code: 2`，前面一切正常，
  而且产物是个**只有 0.5 MB 的半成品**（正常应该 88 MB）。
- **根因**：`NsisTarget.js` 会把刚生成的安装包**再跑一次**（`BUILD_UNINSTALLER` 模式），
  让它自己写出卸载器。这一步依赖 `%TEMP%`，本机的 `%TEMP%` 在受限环境里写不进。
- **解法**：把 `TEMP` / `TMP` 指到工作区里的目录再打包：
  ```powershell
  $env:TEMP='D:\tmp'; $env:TMP='D:\tmp'; npm run dist
  ```
- **教训**：产物大小是最快的自检 —— 0.5 MB 的「安装包」一眼就是假的。

**② electron-builder 每次都要重下 Electron，网络一抖就超时**

- **现象**：`⨯ Timeout awaiting 'request' for 600000ms`（卡十分钟），
  日志里却写着 `downloaded label=electron progress=100%`（说明它在下而不是在用）。
- **解法**：`build.electronDist = "node_modules/electron/dist"`，直接用 `npm install` 装好的那份。

**③ 本机「启动一个新出现的 exe」本身就不可靠**（诊断时务必知道）

- 用 PowerShell 的 `Start-Process` 启动**打包产物的 exe** 会报
  `操作已被用户取消`（`ERROR_CANCELLED`）；同一个 exe 用 `cmd /c` 却能跑起来；
  而 `node_modules` 里的 `electron.exe` 两种方式都正常。
- **判断方法**：别看启动方式，**看程序自己有没有输出**。
  打包版通过 `cmd` 启动时打出了我们自己的 `[奶蛙] 启动中止：…`，
  这就证明**二进制是好的、`main.js` 真的跑了**。
- 另外：**不带 `--no-sandbox` 时一行输出都没有** —— 但这**不是「DSH 会话的限制」**
  （那是更早一版的错误归因，已在 3.4 更正）：真正的原因是**应用所在目录被标了 Low 完整性**，
  Chromium 在沙箱初始化阶段就 `IMMEDIATE_CRASH`。把同一份打包产物放到普通目录
  （如 `D:\Apps\naiwa-pet`），**不带任何参数**就能起来（4 个进程 + 窗口标题「奶蛙」，第七次会话实测 ✓）。
- **要验证打包版的内部状态**，最省事的办法是给它加 `--remote-debugging-port=9333`，
  然后用 Node 连 CDP（Node 26 自带 `WebSocket`）：读 DOM、读素材 URL、`Page.captureScreenshot` 抓它自己的画面。
  这比猜「窗口为什么没看见」快得多（脚本见 `.assetwork/cdp-verify.ps1`、`.assetwork/cdp-shot.mjs`）。

### 3.7 红线：这个坑**不要**这样"修"

第七次会话确认了根因之后，把不该做的事也写下来，免得下一个人"顺手"改坏：

- ❌ **不要把 `--no-sandbox` 写死**进 `main.js`、`package.json` 的 `build` 配置或任何产品代码。
  它是**开发环境的绕行**，不是产品需求；写死等于替所有用户关掉 Chromium 沙箱。
- ❌ **不要给工作区"撕标签"**（`icacls … /setintegritylevel Medium` 之类）。那会削弱隔离，
  而且工作区的标签是环境管理的、随时可能被写回。
- ❌ **不要为了跑通去改系统安全设置**（Defender、ASR、Exploit Protection、AppLocker、ACL）——
  这些和本坑无关（都已排除），改了只会引入新变量。
- ❌ **不要把「必须 `--no-sandbox`」当成环境要求写进文档/README** —— 那是错误归因。
  正确写法是「**应用目录不能被标成低完整性**」，以及「装到普通目录即可」。
- ✅ 该保留的：`启动奶蛙.cmd` 的渐进降级（先正常、失败再降级）、npm scripts 里的
  `--no-sandbox`（**附注释说明是为绕过工作区的 Low 标签**，见 `scripts/ensure-userdata.js` 头部）、
  以及 `scripts/ensure-userdata.js`。

## 8. 方法论教训（都是真金白银踩出来的）

### 8.1 一次只动一个变量

**这次排查里我连续犯了三次同样的错**，每次都导致归因错误：

| 我的判断 | 实际 |
| --- | --- |
| 「是 `requestSingleInstanceLock()` 崩了」 | 崩在它后面一句 `app.getPath('userData')` |
| 「是 `mouseleave` handler 和光标推送打架」 | 加了日志才发现**它一次都没触发过** |
| 「建目录就是根因，因果坐实」 | 那次我**同时**删了一行日志，根本没坐实 |

改成**一次只动一个变量**（移走目录 / 用独立 userData / 程序化点击）之后，才定位准。

> 讽刺的是，这条教训我上一轮**刚写进文档**，转头自己又犯了。
> **写下来不等于做到。**

### 8.2 「我查过了」必须说清楚查的是哪个路径

主控曾经在 `交接-A到B.md` 里「更正」说 `.assetwork/` 和 `acl-recovery/` 不存在 ——
因为检查时 `cd` 进了项目目录，**只看了项目内部**。实际这两个目录都在**工作区根目录**。

**一次范围搞错的核查，比不核查更糟 —— 它会以权威的口吻把正确信息改错。**

### 8.3 不要从缩略图目测下结论

我一度从 5 帧缩略图判断「待机图和大笑帧没对齐」。
用 `ffmpeg -vf alphaextract,bbox` 一量：`laugh_0001` / `laugh_0026` 的包围盒与 `idle_relax`
**完全相同**（x114-265, y44-348）。**目测不可靠，要量。**

> 第四次会话重出了一版素材，这条结论依然成立而且更强：现在
> `laugh_0001`、`laugh_0231`、`idle_relax` 三者的包围盒都是 `x114..265 y44..348`。
> `npm run check` / `npm run probe` 会把这三个数打出来。
>
> ⚠️ 但**「静态和大笑没对齐」这个用户报的现象是真的存在过** —— 只是原因不在素材，
> 在 CSS（第 6.2 节）。同一条现象背后可能有好几层，**量到的那一层才算数**。

### 8.4 没有版本控制 → 宁可停用也不要删除

`CONFIG.RUN_ENABLED = false` 这种「保留代码 + 开关」的做法，代价是 100 多行暂时不执行的代码，
收益是恢复时零成本。**在没有 VCS 的项目里，这个取舍是划算的。**

第四次会话照这条办了两次：`IDLE_TALK_ENABLED = false`（闲置说话）、
以及在 `assets/manifest.relax.js` 里**新增** `laugh_short` 而不是把 `laugh` 改回短的。
素材也同样处理：旧的 26 帧乒乓版归档进 `.assetwork/archive/laugh-pingpong-26frames/`，
没有直接覆盖掉。

### 8.5 未被执行过的检查等于没有检查

`__verify.js` 的 PNG 解析器一直读错数据，但**从没被发现**，
因为当时没有任何槽位声明为叠加层，依赖它的那条检查从来没真正跑过。
**加了新检查，一定要构造一个能触发它的反向测试。**

第四次会话里这条被用成了固定动作：

- `__probe.js` 的布局断言**先在没修 CSS 时跑了一遍**（8 项失败、静态图跑到 `#pet` 盒外 76px），
  修完再跑（25 项全绿）—— 这样才证明它不是一组永远为真的空断言。
- 「闲置不再自动说话」这条，**概率 6% 直接测等于没测**：
  于是把触发条件临时调成「阈值 0 + 概率 1」，先验证「开关关着一定不冒」，
  再**把开关强行打开验证「一定冒」**。后一条失败就说明前一条是空检查。

### 8.6 测量口径本身也会骗人

第四次会话连续碰到两次，都是**产品没坏、是量法不对**：

| 现象 | 真相 |
| --- | --- |
| 静态奶蛙像素包围盒「高度 148.7px 正常」，但实际是被裁成半身的 | 启动 toast（深色实心药丸，顶边正好在 y≈412）和奶蛙被**并成了一个包围盒**。抓图前必须 `prep()` 收掉无关元素 |
| S5「分身严格同帧」报 `不一致分组 1/228`（基线是 0） | 判据是「相邻两次绘制 ≤8ms 就链成一组、每组取每个 canvas 的**最后一次**」。231 帧首轮解码把同拍内的三次绘制拉到 ~8ms，链就**跨到了下一拍**，组里同时出现第 N 帧和第 N+1 帧。三个播放器共用同一个 rAF 和同一套帧计算，帧号不可能算岔 |

**判据：一个检查在「跟它无关的改动」之后突然变红，先怀疑量法，再怀疑产品。**
S5 现在改成按「某个 canvas 又画了一次」切分同一拍 —— 与负载无关。

### 8.7 永远红的检查等于没有检查

跑步功能停用之后，冒烟测试的 S9/S10/S11/S16 会**永远 FAIL**
（断言「闲置 60s 必须跑起来」，而功能是按配置关掉的）。
`__verify.js` 里那条「序列帧 > 2MB 警告」同理：2MB 是 26 帧时代定的，
改成整段 15.4 秒后必然常亮。

这两个都不是产品问题，但**长期亮着的红/黄会训练人整张表都不看**，
真出回归时没人会发现。处理原则：

- **按配置分流，而不是放宽断言**：S9 现在读 `RUN_ENABLED`，
  关着就 SKIP 并写明是哪个开关、在哪儿；**打开就恢复成真断言**。
- **把阈值改成真正要防的东西**：序列帧的真实成本是解码后的位图
  （`帧数 × 单帧像素 × 4B`），不是磁盘字节数 —— 于是改成「位图 > 200MB 才提醒」，
  并把实际位数打进那行输出。
- **绝不为了让表变绿而删掉断言。**

### 8.8 素材一变，测试里写死的时间就全废了

大笑从 1.73 秒变成 15.4 秒之后，`__smoke.js` 里写死的三个等笑上限
（`6000` / `4500` / `4200`）全部不够用：S2/S6 会**假失败**，
S8 更糟 —— 它的「表演结束时刻」有个「测不到就用此刻」的兜底，
于是冷却窗口整体前移，拿上一场**残留的分身**当成了新触发，
**结论和归因都是错的**（报的是「冷却期又触发了分身」）。

改法：时长**只有一个真相来源**，就是 `assets/manifest.relax.js` 的 `count / fps`
（产品侧的 `core/assets.js` 也是这么算的）。测试从清单派生 `LAUGH_WAIT_MS` / `PERF_MS`，
并且 `S8` 改成「测不到就 SKIP，绝不用此刻兜底」。

> 顺带一条：`core/audio.js` 的合成笑声原本也是**写死**「对着 26 帧 / 1733ms 调的」，
> 同样改成了从清单读。**凡是从素材派生的数字，都不该手抄进代码。**

### 8.9 程序驱动的测试会被「真实世界状态」咬一口

第五次会话连续踩到两次，两次都表现为**看起来像产品 bug 的假失败**：

| 现象 | 真相 |
| --- | --- |
| 探针里「右键单击弹出操作窗」**连续失败**，而同一功能的冒烟测试 S17 **通过** | 产品有「光标离开奶蛙就收起操作窗」，由主进程 40ms 一次的光标推送触发。探针是程序驱动的，**真实光标并不在奶蛙上**，菜单一弹出就被下一拍收掉。真实用户右键时光标必然压在奶蛙上（否则窗口还是穿透态，右键根本到不了窗口）。**缺的是探针里那一步：把奶蛙挪到真实光标底下**（`win.setPosition` + 等一次推送） |
| 工作模式冒烟第二遍跑：W4/W7/W8 三项 FAIL（「已有 60 行」「剪贴板 8 条」） | 复验脚本复用了同一个 `SMOKE_TMP_DIR`，上一轮留下的便签/剪贴板还在。而 W4 断言的是**空状态提示**。产品没问题，是**冒烟测试不可重复跑** |

**两条结论**：

- **程序驱动的测试要先把「真实世界的状态」摆对**（真实光标在哪、真实数据文件是什么），
  否则量到的是环境，不是产品。装完这个前提之后，探针 33/33 全过。
- **测试必须可以反复跑。** 冒烟测试现在在主轮开工前会清掉**隔离目录里**的数据文件
  （三个预置数据的补充轮不删）。一项「只能测一次」的测试，第二次就会开始说谎。

### 8.10 环境探测函数：别只报结论，也别用「写完再删掉」判定

第六次会话最贵的一课，代价是一整轮排查。用户双击打包版后弹的是**我们自己写的**框：

> 奶蛙的数据目录没有写入权限，启动被挡住了。
> 数据目录：`C:\Users\33844\AppData\Roaming\naiwa-pet`

而事实是：**那个目录完全可写**（`icacls` 干净、用户有完全控制、用户自己在干净 cmd 里
`echo test > "%APPDATA%\naiwa-pet\hello.txt"` 返回 `ERRORLEVEL=0`、我在自己会话里写+删都成功）。
真正的情况是**应用所在的目录被标了 Low 完整性标签**，Chromium 在沙箱初始化阶段就急停
（见 §3.4；当时误以为「是这台机器的毛病」），
而我的探测函数**自己误报**了 —— 它要求「写成功 **且** 删成功」才算可写，
杀软扫描刚写入的文件时删除会短暂失败（EPERM），于是明明可写也被判成不可写。

**三条硬规则**（都写进代码注释了）：

1. **探测函数必须把真实 errno 和完整路径带出来**。只说「没有权限」，等于把排查的人
   （包括未来的自己）推进死胡同 —— 加上 `EPERM: operation not permitted, open '…'` 之后，
   一眼就能看出那是**沙箱/权限层的拒绝**，而不是 Windows ACL。
2. **判定条件要贴着「我要用这个目录干什么」**。我们只需要「能写进去」，
   却顺手要求了「能删掉」—— 多出来的那半个条件就是误报来源。
3. **不可写要能自救，而不是把用户挡在门外**。现在会先试备用目录
   （`%LOCALAPPDATA%\naiwa-pet-data`），都不行才报错。

> 顺带一条同源的教训：单实例锁失败原来只有「确定 → 退出」，用户被永久挡在门外。
> 现在弹的是**两个按钮**（仍然启动一只 / 退出），因为锁失败常常只是上一次残留状态，
> 过一会儿就自己好了。

## 9. 复核命令

```bash

set SMOKE_WORK_CORRUPT=1  && npx electron --no-sandbox __smoke.work.js
set SMOKE_WORK_BIGCLIPS=1 && npx electron --no-sandbox __smoke.work.js
```

> 上一轮跑挂了、进程还赖着不走时，**换一个临时目录**就等于换一把单实例锁（3.2）。

> 沙箱里 Electron 渲染进程建不了命名管道（`platform_channel.cc ... 拒绝访问 0x5`），
